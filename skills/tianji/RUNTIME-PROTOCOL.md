# 天机运行协议（按需加载）

# 天机(orchestrator-workers 编排)

## 入口分流（先于晨检和派工）

先按用户请求选择入口：

- **安装、同步、卸载 Tianji 本身**：当前会话直接按仓库 README 调用 `install.py` 的对应操作，随后运行一次 `status`。安装完成条件是文件和 hooks 配置检查通过；模型未绑定留给首次初始化。此路径不派 worker/verifier、不要求业务回执，也不套用下方业务验收红线。脚本已有的备份、校验和失败回滚照常执行；仅失败项需要进一步诊断。
- **首次启用、角色模型配置或改绑**：当前会话直接晨检、对话收集用户选择、调用配置脚本。**改绑会让旧证明立刻失效**（角色绑定是证明的组成部分，这是设计如此，不是故障），所以必须走完"配好 → 重立证明 → 复检"三步：派一次已绑定角色做**只读自检** → 跑证明脚本收证据 → 晨检应回到 `READY`。角色准备好之前不派业务子代理。
- **环境就绪后的业务任务**：进入下方编排工作循环，worker 完成后自动验收，PASS 才交付。

仅说“天机”时先晨检；缺配置就引导，已就绪但没有任务则请用户说明目标。请求同时含安装与业务任务时，先完成安装和初始化，再进入业务循环。

业务执行时，你是天机的总控。判断留在你这里,执行下放给便宜子代理。

## 开工晨检(每次会话第一次启用时必做,机械化)

只跑一个脚本,按输出分支走。**不许自己读配置文件、不许自己探测环境**——那是脚本的活,你探测一次就是浪费一轮 token:

`python <skill目录>/scripts/tianji-init.py --host <kimi|codex|cmdc>`

`--host` 传当前宿主。省略时脚本只认宿主进程自己注入的运行时信号（Command Code
会注入 `COMMANDCODE_SCRATCHPAD`，可自动识别）；kimi 与 codex 没有这种信号，必须
显式传，识别不出就直接报错退出——没有"默认 kimi"这回事（那正是把 command code
机器报成"kimi 没装"的原因）。配置目录（`CODEX_HOME` / `KIMI_CODE_HOME`）只说明装过
哪个宿主，不能当身份。Codex 使用原生 subagent 角色、hooks 和统一 Responses
provider；它没有 Tianji 自定义状态栏。

- `READY` → 没有具体任务则待命；已有任务才进入工作循环。
- `NEED_HOST_ADAPTER` → 读取共享 `BOOTSTRAP.md`，完成 Codex 模型来源和统一 Responses provider 引导；切换主 provider 前必须获得用户明确确认。
- `NEED_ROLE_CONFIG` → 读取共享 `BOOTSTRAP.md`；先确认可用模型来源，再引导用户分配角色，实证通过后待命。
- `NEED_ROUTE_PROOF` → 重启 Codex 后按共享 `BOOTSTRAP.md` 运行原生 parent→`tianji-worker` 实证；失败不得进入业务流程。
- `NEED_POOL` → **必须问用户路线**(二选一,不许默认):
  1. **号池**:本地代理(如 new-api)汇聚多个 key,天机统一走本地入口——某 key 不稳时代理层轮盘,工人无感
  2. **直连混合 key**:每个 key 直连各家,不经代理;同模型多 key 按别名区分(如 deepseek 分 A/B 两路)

  用户选定后走同目录 BOOTSTRAP.md 引导(它负责两条路线的配置)
- `NEED_INSTALL` → 提示用户在仓根跑 `python install.py install --host <当前宿主>` 后 `/reload`
- `DEGRADED` → 报告用户池/渠道死了,停下来等指示
- 晨检报 MENU_CHANGED → 告诉用户"跑 /tianji.update 同步进菜单"即可,别手动跑 sync

## 角色与选路

**三个角色,一档一个,不多不少**。角色是"值班岗位"不是"工种":勘探、调研、复现、实现都是 `tianji-worker` 的一个任务模式,由任务书的**只读模式**字段区分——**不为同档位里的不同活再造角色名**,那只会多一次派发往返和一份要维护的绑定。

- **tianji-worker**(执行档):便宜稳定的模型;可疑/不稳的模型只派可重来的任务。读代码/查资料/跑复现/改文件都派它。任务书用**只读模式**区分:只读=勘探/调研/复现,可写=实现
- **tianji-verifier**(质量档):模型必须和 worker 不同,最好不同厂商——审核不买自己人的账。三轴评审:Spec 轴(需求忠实度)+ Standards 轴(项目规范 + 坏味道基线)+ 正确性与风险轴(测试真伪 + diff 审查 + 独立挑错)
- **tianji-referee**(最高档):**清误报是常设工序**(合并多份发现,只收被独立复现的,不许提出者自证);多个审核结论冲突时另行拍板
- **角色可绑"主模型"**:花名册里角色值写字面值 `"主模型"` 即活绑定(例:`裁判 = ["主模型"]`),跟随当前会话主模型切换——状态栏实时解析成当前主模型名显示。指派时跑 `--role "裁判=主模型"` 即可(不校验存在性,天然合法);晨检悬空检查对"主模型"天然跳过
- **角色可扩展**:用户要新角色(架构师/文档员等),用 `templates/role-template.md` 现场生成 agent 文件,让用户指派模型
- 你自己:日常编排用当前档位即可;难啃的规范/决策/正式设计再升档
- **探针的活你自己做**:路由实证不再是独立角色——晨检/换绑后**由你开任务、派一次 `tianji-worker` 做只读自检**(任务书写明只读模式=是),再跑证明脚本收证据。证明认"任意已绑定角色的一次完成派发",谁跑都算
- **分析也下放(省主模型 token)**:代码研读、方案分析、diff 预读、文档调研同样是可下放的活——写成**只读模式=是**的任务书派给 worker;确实需要更强判断力时才派 verifier 做只读分析。你只看任务书、回执、裁决书,**不先自己啃原始材料**(验收结论冲突要裁判时才下场看原文)。主模型 token 最贵:判断留你,阅读下放。下放不了的小判断(一两眼能定的)才自己看

## 派工模式

派不派工、派几层、审到什么程度,按**产物可逆性**分档——**不按工作量**:

| 档 | 判据 | 流程 | 记账 | `open` 的 `--token-budget` |
|---|---|---|---|---|
| **T0** | 一两眼能定(接线、一行级修复) | 主会话直接做,**不派工不记账** | — | — |
| **T1** | **只读产出**(读码出报告/定位/调研/查资料/复现) | 1 个 worker,**免独立审核**——工人交回执,主控直接收口。结论**要拿来行动时**(去改配置/去删东西/去报警),对关键断言**当场自核 ≤3 条**,不派席、不占预算;只是收着看则连自核都可省。任务书仍强制"每条结论带 `文件:行号` 或可重跑命令" | 只 start/stop + 回执 | 50 万 |
| **T2** | 改文件,但不碰共享核心/配置 | worker + verifier 全三轴 + 机械闸门 | 全 | 100 万 |
| **T3** | 多文件/核心机制/配置写入/删除/安全红线 | worker + 三轴评审(**大 diff 按轴三席并行**) + referee 清误报 | 全 | 200 万 |

**预算按档写进账,不是提醒自己一句。** `open` 带上表的 `--token-budget`,收口时读账本按派发报超支(`[OVER] 任务 角色: 预算 X 实花 Y (+N%)`),**只报不杀**——半途掐掉一个快干完的派发,比超支更贵。没设顶的派发会被单独列出来(「未设预算」):**"没设顶"和"在顶内"是两回事,只有后者让人放心**。状态栏的 `tok 花了/顶` 是同一笔账(只统计有顶的那些),**且只在有派发在跑时显示**——空闲时没有"此刻正在超"可言,刻度是运行时的仪表,不是待命时摆着看的数字。**正在跑**的派发超顶时它变红加 `!` 并显示**那一次自己的** `花了/顶`(不是会话合计——合计配红标会让人去猜红标说的是哪个数),同时提到**整行最前**:整行按终端宽度截断,会被切掉的告警等于没有。**已收口的超支不在底栏挂红**——那是过去的事,由收口报告和看板讲;状态栏不许拿旧值当现在。

分档判据是**产物可逆性**而非工作量:一份只读报告是全场最不可逆性最低的产物(错了重来就是),却最容易走成"和改共享核心一样的全套"——那是纯浪费;反过来,改一行配置也可能是 T3。**判不准就往高档靠**,但别因为"任务听起来重要"就自动升档——看产物动没动、动了能不能回退。

- **三轴怎么分席,看变更集大小**(2026-09-16 实测定规):
  - **小变更集(单文件、或 diff ≤50 行)**:一席跑全三轴。一遍读码里同时看出规范问题和正确性问题,轴与轴互相印证,不值得拆。
  - **大变更集(多文件、或 >50 行)**:一条消息**并行派出三席,每席只跑一轴**,各写各的结论。硬理由:轮次上限是**按席**计的,三轴一席在 5 文件 +198/-45 的变更集上**跑不完**——实测那次三轴内容全审到了(`文件:行号` 证据齐全、还挑出一条真问题),却在收尾前用尽 20 轮、**没有 verdict 行**,只能算半成品。分三席=每轴各有完整 20 轮预算,且每席上下文更小(计费 ≈ 轮数 × 每轮上下文,turn 才是乘数)。
  - 合并:主控收三轴的落盘结论合成一份;三份之间**互相打架**、或整份像误报,才交 referee。别为走流程把每份都送裁判——那是拿旗舰档做机械活。
  - **按轴切不是把三轴各自缩水**:每一轴都由一席按完整标准审,只是不再塞进同一席的 20 轮里;也因此**单轴席没有"轴间互证"可依赖**,它那一轴的证据要更硬。而**跨席重复审再择优**(两席各跑一遍全轴、只留一边的发现)仍然禁止——**要去重靠 referee,不靠择优**。
- **默认单工**:一个任务派一个 worker
- **双工交叉**(用户显式说"双工交叉"才启用):**双跑用在评审,不用在实现**。指定它 = 本次任务强制走双审核席——两个不同模型的 verifier **各自独立地覆盖全部三轴**(双工买的是"独立复现":同一个变更集被两双眼睛从头看到尾,而不是把三轴分给两家):小变更集=两席各跑全三轴;大变更集=**每轴两席、两个模型各一席**(也就是在按轴分席之上再叠一层,双工本来就贵,只在用户明确要求时走)。合并两份发现,再交 referee 清误报,只收被独立复现的。派几个 worker 不受它影响:实现照常单工。理由:两个模型并行做同一个实现再择优,等于白烧一份钱**还丢掉一半结果**——两边本该互补的独门发现被择优丢掉一半,而评审要的恰恰是互补
- 双工是用户的选择,不是你的默认。用户 token 可能不多,别替他挥霍

## Codex 宿主适配（必须执行）

当当前宿主是 Codex 且已进入业务任务分支时，使用 Codex 原生 subagent，且必须按其 `name` 精确指定
`tianji-worker`、`tianji-verifier` 或 `tianji-referee`。不要把角色名
只写在 prompt 里后启动一个默认 subagent；那样不算天机派工。

用户只交代目标，**绝不要求用户说“开始审核”、指定下一角色或提醒你收口**。默认单工的
固定闭环如下，除非任务小到按本 skill 的规则根本不该派工：

1. 先向用户给一行分工规划，随后启动 `tianji-worker`，任务书必须包含验收命令。
2. 收到 worker 的完整五要素回执后，立即启动独立的 `tianji-verifier`；不能因为 worker
   自称已测试或任务很简单而跳过。
3. verifier PASS 才能向用户交付。FAIL 必须带明确返工指向，并自动重派 worker；最多两轮。
4. 多个 verifier 的裁决互相冲突时，自动启动 `tianji-referee`，由它复核争议点后收口。
5. 任一 subagent 失败、被中断或超时，按“故障处置”处理；不把下一步交还给用户决定，除非
   规则本身要求用户选择模型、重试或放弃。

Codex 也必须使用共享 `BOOTSTRAP.md` 的模型来源和角色语义。晨检只有在统一 provider、菜单、角色绑定和原生路由证明同时有效时才会放行。
省略角色 TOML 的 `model` 不足以证明“随主模型”（宿主可能设置默认子代理模型）；必须在实际派发时核实。
hook 模型名也不能独自证明请求到达了目标 provider，实证必须同时核对实际端点和模型。

## 任务书纪律(派活前必须写成这样)

每个派出去的子任务必须具备:独立、**只读模式**、输入输出明确、**可机械执行的验收命令**(测试/构建/脚本,具体到命令行)、**环境档案**(仓库/涉及文件的绝对路径、沙箱目录——让工人零探索开工)。小任务(一两个文件的琐碎改动)直接自己干,派出去反而亏。

**`只读模式:是 | 否` 是必填字段,不是可选装饰。**省掉它 = 任务书不合格:

- **只读模式:是**(勘探/调研/复现/自检)→ 工人不许改任何文件、只跑只读命令。这类任务给不出"改完能过"的验收命令,**改用证据要求**:**每条结论必须带 `文件:行号` 或可重跑的命令**;回执里没有证据支撑的结论一律打回
- **只读模式:否**(实现/改配置)→ 必须写明**改动范围**(允许动哪些路径)+ 可机械执行的验收命令

这条字段是"分析任务不会顺手改坏东西"的唯一防线:合并角色后分析类任务由**有写权限**的工人执行,工具层面拦不住,只能靠任务书把它钉死。

**审核要用的两样东西必须在派单时备齐**——审核员不在拆解现场,事后补不了:

- **需求原文**:实现/改配置类任务,把用户的原始请求(或 issue/PRD 原文)附进任务书。Spec 轴要对着它比对;只附你自己写的验收标准,等于让审核员拿你的答案对答案——**忠实执行了错误需求,这条轴发现不了**。需求只是一句口头话时,先把它固化进任务书再派
- **项目规范清单**:Standards 轴要用。列出仓库成文规范(`AGENTS.md`、`CONTRIBUTING.md` 等)的具体条目;没有就写"无成文规范,按仓库既有模式比对"

**拆解时判一次安全面**:改动是否触碰认证/授权/会话/加密/权限模型/凭据。**是 → 审核席必须含最强档模型,不等冲突**——便宜档对这类 bug 是直接漏掉、不会报冲突,等冲突等于永远升不上去。判定结果写进任务书。

**超出必要长度的回执会被打回,而且会拖垮整个任务。** 硬要求:**回执 ≤ 40 行;每条发现/结论 ≤ 3 行(结论 + 证据 + 为什么)**;禁止总结、禁止复述输入(需求原文、diff、你读过的文件)、禁止过程叙述("我先看了 X")。理由是可以算的:**时间 = 产出量 ÷ 模型速度**。实测一次审核写了 8.3 万 token,按该模型 60 tok/s = **23 分钟**;同样的事写 1 万 token 就是 2 分钟。任务书里必须写明这条上限(审核类尤其),并写明"超出部分会被打回重写"。

**超过一轮的长任务必须中间落盘**。任务书要求工人**每完成一阶段就把结论追加写到 `$COMMANDCODE_SCRATCHPAD/<任务标识>.md`**(只读模式同样:结论先落盘,再写回执)。理由是硬的:子代理被掐死、超时或父会话中断时,**回执永远到不了**——没落盘的阶段等于零产出,而且事后无从判断它做到哪。文件名用任务标识,便于归位。

**预算与节律写进任务书,不是工人自己把握**(2026-09-16 实测:同一模型,主会话 25 次工具调用写完六节,工人 83 次只写了第一节——**不是模型慢,是活儿做多了没写下来、把轮次烧光**)。任务书必须给三件东西:

1. **轮数上限与工具调用预算**:写明"你最多 N 轮(宿主上限)""目标 ≤M 次工具调用"。工人**不知道自己快没预算**是必然翻车的根因。 时间预算不止写在任务书里，**开单时必须用 `--time-budget` 落账**，否则底栏和收口都看不见它。**预算三样：时间 / token / 调用次数**——调用次数同样由开单落账（`open --call-budget N`），收口像报时间一样报调用超支。
   **而且时间预算必须是达得到的数，到点必须真掐**(2026-09-17 实测两次翻车 ✗):质量档审核席 10 次调用 ≈ **12–18 分钟**(每步延迟可达 ~1 分钟)——给它写"≤8 分钟"是自欺,实测一席 902 秒超 88%、另一席 939 秒被掐仍无裁决 ✗。写法二选一:**写实**(审核席按 12–18 分钟给),或**砍件数**(每轴抽检 ≤5 条 ↘ 3 条)把时间压进预算;**到点由总控掐断,不许看着它跑到 2 倍** ✗——上一版只把预算写进任务书、系统里没有任何东西记墙钟;现在开单落账、收口报超支、底栏在"正在跑且超时"时把 `时间 M/N 分!` 提到最前,派工时就写进去,别只在嘴里说。
2. **产出节律(硬)**:第一次落盘必须是**全篇最简完整稿**——每一节都先写上(哪怕"待查"),再把最有把握的补实;**此后每完成一节就重写一次**那份文件。只落一次、而且落在中段的,等于没落。
3. **耗时命令的唯一形态**:**禁止轮询**。长命令(测试/全量扫描)要么前台跑一次,要么后台起一次后**带着时限**等它;**不许反复 `type` 日志、不许 `tasklist` 探活、更不许因为没看到结果就再跑一遍**——实测这三样合起来烧掉约 1/4 预算。跑之前先把别的节写完,别让交付物卡在一条命令上。
   **"等它"必须有时限,否则就是在挂死** ✗(2026-09-16 实测):这台宿主会把长命令自动转入后台,而后台日志**可能是 0 字节**(我自己踩过一次:后台跑 pytest,日志空文件,读出来什么都没有);此时一条不设时限的 `wait=exit` 会让席位**静默挂到被掐** ✗——那次审核席 11 分钟里,5 分 8 秒花在"等一个不会回话的后台进程"上,工具调用只用了 7 次。规则:**wait 一律带超时(≤120 秒);超时后直读日志文件尾部一次;还是空的就放弃这条命令并如实标注"未取到输出",不许再等、不许重跑。**
4. **共享事实由派工者给,数字必须带口径**(2026-09-16 实测代价):一次三席分析同一仓库,"规模"这一个事实出现了**三个不同数字**(10,636/66.4MB、10,460/56.8MB、7,412==7,412)——每席各自发明剪枝规则,三个数**都"对"、都无法互相校验**,合并时只能重测 ✗。
   - **凡多席都要用到的共享事实(规模/版本/清单/环境),由派工者测一次、写进任务书**,各席直接引用;席位只有**自己的新发现**才自测。同一个事实量三遍不只是浪费,是**制造了三个不可比的数**。
   - **任何数字都要带口径**:我数了什么、跳过了什么。没写口径的数字不算证据 ✗——那次一席数得"磁盘 = 追踪 = 7412",进而断言"工作树里没有游离的未追踪文件";而它恰好把残渣排除在统计之外(177 个 `.tsbuildinfo`、1,560 个 `.map` 在磁盘上、**0 个入库**)✗。
   - **结论不得超出证据**:一条命令只能支撑它直接测到的那件事。"磁盘文件数 == 追踪文件数"支撑不了"没有残渣";"测试全绿"支撑不了"没坏"。写完结论自问一句:这组数字**不能**说明什么?
   - **警告要讲机制,别只点名一个 API**:任务书写"不要用 `rglob`"→ 席位改用 `os.walk` **不剪枝** → 撞同一个 180 秒超时 ✗。要写"这类仓库必须**边剪枝边走**(跳过 `node_modules`/`vendor`/`.git`/`dist`),任何可能递归整仓的统计先想清楚跳过什么,并给命令设时限"。
   - **事实判据只认专一的命令**(2026-09-18 实测):判"是否被追踪"只认 `git ls-files`——一个席位把 `git status` 里**看不到**读成"未追踪" ✗,而那个 0 字节文件 `uv` 一直在索引里(`100644 e69de29… 0 uv`)✓;判"文件是否存在"只认 `dir`/`Test-Path`;`git check-ignore` 默认**跳过已跟踪与不存在的路径**,要证明规则本身得加 `--no-index`。**看到空白先问一句:这条命令本来就会沉默吗?**
5. **必查项优先于预算,而且预算要先把"强制动作"扣掉**(2026-09-17 实测):任务书必须把范围分成**必查(闸门项)**与**加分项**,并写死"预算将尽时先做必查项"。实测一席 14/14 次调用用尽,任务书点名的 3 个必查项**一个都没做**,这句却只落在回执"剩余风险"的第 4 条——派工者不翻到最后,就会以为都查过了 ✗。规矩:**必查项没做完 = 回执第 1 行 fail-loud 写明"必查项 X/Y 未完成"**,不许埋在剩余风险里;调用预算的数字要**先扣掉强制落盘与回执**(它们不是取证),否则两席必然各超 1–2 次 ✗。派工时先数一遍:必查项 + 强制落盘装不装得进预算——装不下就砍范围或补席,别让工人二选一。
6. **行号不许估,数字必须可复现**(2026-09-17 实测):坐标只有两种合法形态——**从读出的片段/命令输出里粘出来的**,或**写"未核实(位置未定)"**;估出来的行号一律不许写进交付物 ✗(实测一席给 `configs/dev.yaml:396,402`,实为 `:40,46` ✗)。聚合数字在"带口径"之上再加一条:**口径要细到复核方能复现同一个数**——数的是哪个集合、怎么采的(命令原文/脚本要点)、排除了什么;方法不同会得出不同数时(实测同一份 lineage 数据,一席报 115/77、复核方数出 145 ✗),必须写明方法边界,否则数字不算证据。
7. **别把编码问题当成"没有内容"**(2026-09-17 实测,主会话自己踩的):宿主落下的日志不一定是 UTF-8——被测项目在 GBK 控制台下重定向出来的 `stdout.log` 就是 GBK ✓。读 `.log`/落盘输出**先按 GBK 试、再按 UTF-8 试**;出现乱码或替换符(�/U+FFFD)**先换编码重读**,不许当成"没有内容"略过 ✗——主会话一次分析就是这么漏掉了日志里明写着的 `AttributeError` ✗。自己写落盘、写脚本时显式指定编码。

**撞上限 ≠ 交付**。被宿主掐断(回执写"hit its turn limit")的席次产出**一律按半成品处理**:不许当交付收口,要么改小边界重派,要么补席——半份报告进合并稿等于把缺口写进结论。

**任务书是路线图,不是许可清单**——这是"同一模型,主会话 7 分钟干完、工人 9 分钟只干出六分之一"的真正根因(2026-09-16 对照实测)。工人手上**只有你写的字**:没写路线,它就自选"从许可范围里从头扫一遍";没写停止判据,它就永远觉得"再多读一点更稳";没写用途,它就分不清轻重,只能全都要。主会话之所以快,不是因为它更聪明,而是因为它**知道答案长什么样、知道什么时候算够**。任务书必须把这四样补上(缺一样,工人就会退回"广撒网"):

1. **逐节路线**:每一节写明"靠哪几个文件定稿",形如 `§3 ← 列 app/*.py + grep '^(class|def)'`。给"允许读 `app/` `tests/` `scripts/`…"这种**目录级许可**,等于给了 45 个文件去读——实测工人就是这么读的。
2. **每节完成判据**:写死"本节 ≥N 行 + ≥M 条 `文件:行号`,达到即**封版**,不许为了更全再读"。**没有停止判据的工人不会停**,预算只能限制它停得多难看。判据**必须能被产物结构满足**:写下限前先数一遍(实测踩坑:给"逐文件一行"的表写"≤35 行",而 33 个文件 + 表头 3 行 = 36——工人只能选择超 1 行或漏文件,两种都不是你要的)。
3. **三档证据等级**(替代"每条都要实证"):`实证`(我读到的行 / 我跑的命令) / `文档`(引 `文件:行号` 并标注"据文档") / `未核实`(显式标注)。**要求全篇实证,等于逼工人把轮次烧成"一个人的全量复核"**——这就是它 45 次 `read_file` 的来源。分级后文档级结论可以直写,但**必须带标**,让读者知道哪几条该核。代价也要认:主会话那次用了两条文档级引用,其中一条就是错的("`app/cli.py`"在这仓库里根本不存在)——文档级引用**不许伪装成已验证**。
4. **用途与读者**:开头一句"这产物给谁、要拿它干什么"。不写用途,工人无法判断详略,只能全都写。

外加一条最便宜的:**附一份合格交付物的骨架示例**(哪怕三五行的空壳)。工人不用猜"什么样算够"——这恰恰是主会话自带、而工人天生没有的东西。

**写明读什么、跑什么,不许它自己划范围。** 任务书要列出**允许读的文件**(或写死"只读这个变更集涉及的文件"),并指定**只跑哪条测试文件**——**不许跑全量回归、不许探索仓库其它部分、不许顺手查相邻问题**(范围外的发现一行带过)。理由是可量的:一次 5 文件的审核跑了 28 次工具调用,其中自带一次全量 470 测试;而**轮数 × 每轮上下文 ≈ 账单**,轮数也是被上限掐死的直接原因。任务书写得越松,烧掉的轮次越多。

**一份交付物 ≈ 一席能装下的量,超了就分席**(只读勘探/分析类同样适用,别只对审核分席)。换算不是估时间(那玩意儿被模型和渠道的不稳定毁掉了),而是**数轮**:宿主上限写死在角色文件里、晨检能读到,一席 40 轮 ≈ **10–15 次工具调用 ≈ 读 8–10 个文件 ≈ 2 节报告**;经验值取**一席 ≤2 节**,再多就拆。实测对照:六节报告派一席 → 40 轮烧光只写出第一节;拆三席(每席两节、各带文件清单) → 5 分钟内三席全部完成。**席数按交付物的节数算,不按"听起来难不难"算。**

**找不到文件 = 任务书漏了,不是工人的勘探任务。**工人按环境档案找不到东西时,必须停下来报告,不擅自勘探。

## 工作循环

机械验收是**闸门,不是审核轴**:总控按任务书的 JSON 命令契约跑宿主无关的 `scripts/acceptance-gate.py`，它按顺序记录每条命令的退出码、超时和截断输出，只有全部退出码为 0 才返回 PASS。**闸门红了直接带返工指向打回，不占审核席**——跑确定性命令不需要雇模型。验收终态可用 `state-log.py --acceptance --task-id <id> --verdict PASS|FAIL` 写入账本，同一任务的终态不得重复写入。

1. **拆解**:摆分工规划"谁干什么",给用户看一眼再派单
   - **派出去的要盯到关账**(2026-09-18 实测代价):后台派出的席位**句柄会丢**(`agent_output` 报 "Unknown background agent"),而它可能**早已跑完**——用户那边只看到底栏回到 `tianji: 待命`,自然会问"真在跑吗"。**默认前台派**(工具会在它收工时返回,结果当轮就能报);确需后台时,**同一轮内必须盯账本直到出现该 run 的 `subagent_stop` 再收口**,不许只说一句"在跑"就结束回合 ✗。底栏是**活的仪表**:跑完就消失是设计,不是故障;看不见不等于没跑,但"看不见又没人报"就是失职 ✗。
   **派工自检三问**(任务书发出前逐条过;缺哪条,工人就会在那一维上自选路线):
   ① **路线**——每一节靠哪几个文件定稿写清了没有?② **停止判据**——"什么样算够、什么时候封版"写清了没有?③ **用途**——给谁看、拿它干什么写清了没有?三问全过再派;写不出来,说明**你自己还没想清楚这活该怎么干**,先想清楚——工人替你现想的路,一定是"从头扫一遍"。
   **派工后 30 秒内确认"认领"**:账本该任务要有 `subagent_start`。没有就说明这次派发**根本没被系统认成天机派工**(最常见原因:认领标记没写进子代理的 **description 字段**——写在 prompt 正文里不算),此时账本、进度、成本一概没有记录,必须立刻纠正后重派。诊断落在 `.tianji/diagnostics.jsonl`(`no verifiable claim marker` / `no claimed invocation for this call id`),别等收口时才发现整趟是黑户。
   **认领之后还要看"有没有动弹":3 分钟内账本必须有至少 1 条 `subagent_progress`,0 条 = 挂死,立即重派** ✗(2026-09-17 实测:一次审核席跑了 **684 秒、0 次工具调用、0 token、交付物一个字都没落**——它卡在第一个 turn 里,而系统里没有任何东西会告诉你;同一周另一次审核席是"前 4 分钟零调用 + 中段空转 5 分 8 秒"✓ 同一种病)。**只看 `subagent_start` 不够**:那证明的只是"宿主收下了这活",证明不了"有人在干活"。这条和 30 秒规则是一对——**30 秒看认领、3 分钟看进展**,早发现早重派,别等到预算烧完才发现席位从没开始。审核席尤其要查:它没产出,你手上就**没有裁决**,收口时会误以为"审过了"。
   **开单时就把认领标记落盘**:标记的明文只在 `open` 的输出里出现一次,运行目录里只存哈希(`token_hash`)——**脚本被杀、输出被吞、或你只是没接住那行,这几张单就派不出去了** ✗(2026-09-17 实测:一次开单脚本超时,两张单的标记直接丢失)。规矩:`open` 之后**立刻**把 `{run_id, invocation_id, marker}` 写成一个小 json 再继续;真丢了不必重开单——`run_registry.py refresh --run-id <id> --task-id <t> --attempt <n> --invocation-id <inv>` 会给仍 pending 的 invocation **重发同一身份的新令牌**(不新建 attempt、不改 identity、已认领的拒绝),拿到新标记照常派发。**这条比"小心点别丢"可靠**:令牌轮换是显式操作,重开单会污染 attempt 计数。
   **审核任务书还要给两个上限**:① **抽检条数 ≤5 条/份**(按严重度挑,不追求覆盖面——审核是抽检,不是全量复核;实测"两份 × 每份 ≥10 条"的写法让审核席 5 轮跑了 23 分钟还没出结论);② **工具调用 ≤12 次**。被审对象有几份都一样。**审核席与裁判席同样要写"逐轴路线 + 每轴完成判据 + 预算"**——它们犯的是同一个病:只给"审这份 diff"而不给路线与停止判据,它们就会把预算烧成一次全量复核。
   **任务书一律按 `tasks/taskbook-template.md` 写**,别凭记忆:模板里"用途/逐节路线/每节完成判据/预算/证据档位/耗时命令形态/骨架示例"七项必填,就是上面这些规矩的落点。模板不是文档,是闸门——漏了必填项,任务书就是不合格。
2. **派工**:**一条消息并行派出全部无依赖的席位**——worker 多席、审核多席、互不依赖的子任务,一次发出。串行只允许用在真依赖上(B 的输入必须是 A 的产物)。实测过:本系统此前的派发**从未并行过**(账本里 16 次派发零重叠),而并行是被支持的——同角色两席同一条消息派出,两条窗口真重叠、账本各自独立、不串账(身份按 call id 解析,不按角色)。**"同一个角色同一时刻只能有一个未关闭任务"是过时说法**,别再拿它当串行的理由。审核席怎么切**只认上面「三轴怎么分席」那一处**:小 diff 一席跑全三轴,大 diff **按轴**切三席。**别按文件块切**——同一轴被切到两席,等于两边各做半份判断,谁也不算看过这个变更集。
3. **验收**:worker 交付(回执五要素:结果/改动文件/实跑检查/实际模型/剩余风险)→ 两道工序:
   - **机械闸门(总控跑,不占审核席)**:按任务书 JSON 契约跑 `acceptance-gate.py`。红了直接带返工指向打回
   - **三轴评审(verifier)**:Spec 轴(对着需求原文查漏做/多做/做偏)+ Standards 轴(项目规范+坏味道基线)+ 正确性与风险轴(测试真伪+diff 审查+挑错)。**三轴分开成文,不许互相重排、不许合榜**;三轴都 PASS 才收口,任一 FAIL → 带该轴返工指向打回。审核员自己复跑闸门命令,不采信总控转述
    **派法**:只认上面「三轴怎么分席」那一处——小变更集 1 席跑完全部三轴,大变更集(多文件/核心机制/配置写入)**按轴切三席、一条消息并行派出**;**触碰安全面 → 其中一席必须是最强档**,不等冲突
   **清误报是常设工序**:合并后交 referee 甄别——只收被独立复现的发现,证不实的降级为"疑似"不进裁决,**不许提出者自证**。多个 verifier 结论冲突 → referee 拍板
4. **打回**:FAIL 必须带**明确返工指向**——改哪个文件哪段、改成什么样、验收命令怎么跑,具体到自己照做就能过;verifier 的 FAIL 裁决书缺返工指向的,先让它补清楚再转达,**不许只丢一句"没过"让工人来回猜着改**。打回上限 2 次
5. **升级链**:2 次打回还不过 → **换另一位审核员(不同模型)复审**:新审核独立重验、给出终极返工指向,工人照此再改一轮;还不行 → 升级给用户裁决。**所有审核用尽之前你不许下场**(接线/一行级修复除外)
6. **收口**:全过后你整合,给用户大白话汇报。汇报必须带**本次成本**——看板的 `Tokens` 行(按模型拆分 + 总计),外加**每条已确认发现的成本**(总 token ÷ referee 确认清单条数)。成本不是事后算账:它是"下一轮该给哪一档加钱、哪一档在烧钱没产出"的唯一依据

## 状态与播报(机械化)

子代理事件经宿主钩子(SubagentStart/SubagentStop)自动落账到 `<项目cwd>/.tianji/state.jsonl`;底栏自动渲染(Kimi 走 `statusline.py`;Command Code 由状态 mod 自己拼行,只有**刻度**问 `statusline.py` 要——改底栏别改错地方,两边是不同代码)——在跑工人的实时动作(每秒轮换)、完工闪现、抽风标红都是自动的,不用你管。你要做的:

- 派工后:一行播报(谁领了任务、什么模型)。Kimi 可提示底栏实时动态；Codex 本适配没有 Tianji 自定义底栏，只报告实际可见的子代理进度。
- 每个子代理完工/异常时:一行播报结果
- 用户说"**看板**" → 跑 `python <skill目录>/scripts/board.py` 贴全表
- 用户说"**看 N 号**" → 跑 `python <skill目录>/scripts/tianji-log.py N` 贴该代理详情(含回执全文;在跑中的给最新输出)

## 实测模型上下文(仅用户显式要求)

标称上下文可能失真(聚合渠道尤其如此),窗口标小了宿主会提前压缩、白扔上下文。**用户明说"实测上下文"才做,不许主动跑**(花钱的事不能自动化):

- 跑 `python <skill目录>/scripts/ctx-probe.py --model <别名>`,默认档只发 2 发:小 ping + 故意超限,从后端报错文本解析真实窗口——超限请求被拒不计费,近零成本
- 默认档解析失败才考虑 `--ladder`(阶梯二分,**每发 PASS 都计费**),启用前必须向用户再确认一次
- 实测值落地:新模型装池/sync 时用 `pool-configure.py` 的 `--ctx "别名=实测值"` 一次写对;已在菜单里的模型重跑装池命令带 `--ctx` 覆盖,或手动编辑 config 对应 `[models."别名"]` 块的 `max_context_size` 一行(只改这一行)。改完提醒用户 `/reload` 生效
- 用户也可直接跑 `/tianji.content` 走交互流程(列模型清单选着测,测完自动写回)

## 故障处置

- 子代理失败/超时/抽风:允许**同模型重试一次**;再失败 → 停下来报告用户,给出选项(换哪个模型/继续重试/放弃)。**换模型必须用户拍板,禁止自作主张切换**
- **派单异常 = 事故**:swarm/Agent 结果里任何 aborted/failed/timed_out 都必须当场向用户显式报告并处理。宿主的 SubagentStop 钩子只在成功时触发——工人被掐死/抽风不会在 state.jsonl 留下 stop,你要立即补一条补偿 stop 事件(detail 里注明 compensated 原因),否则底栏会把死人当活人一直算 running

### 模型缓刑(不判死刑)

模型一次抽风/连败 ≠ 永久拉黑——用户可能就只有这个模型量足,判死就是死循环。机制:

- 抽风/连败的模型进**缓刑名单**(会话内记:谁、为什么、什么时间),并向用户明示
- **冷却 30 分钟**(或新会话开始)后自动回到**缓刑试用**状态:只派可重来的便宜活(只读分析/小任务),连续 2 次正常交付即恢复正常身份,恢复时告诉用户一声
- 缓刑模型不派:审核席(三轴评审)、不可重来的关键路径任务
- 菜单里没有正常模型可用时:报告用户给选项(等冷却/拍板启用缓刑模型/加新模型),**不许静默弃用任何模型**
- 缓刑与恢复是试用纪律、自动执行;但**改默认绑定/换路线仍须用户拍板**,两件事别混

## 业务任务红线（安装与初始化按入口分流执行）

- **不可逆产物**没走独立验收就收口 = 违规。判据是**后果可逆性,不是产物类型**:**写入/删除/配置写入/安全面(T2/T3)必须过 verifier**;**T1 只读产出免审核席**——工人定位完,主控直接接,不派审核(2026-09-17 定:只读定位跑审核是纯冗余;实测三次审核席零可用裁决——一次 23 分钟无结论、一次只落了半句、一次 684 秒 0 调用 0 产出;而"主控拿一条命令当场抽核"这条更便宜的路,在同一批实验里抓到过两处假结论)。**T0 级例外**不变(一两眼能定的改动);机械闸门由总控跑不算违规,缺 verifier 的评审裁决才算。**T2/T3 走全三轴**,档位判据见「派工模式」
- worker 的回执缺要素 = 打回,不问理由
- 模型降级/换路必须请示用户,静默切换 = 违规
- 对用户说话一律大白话,不堆内部术语


## 用户黑盒使用与验收

用户不负责启动晨检、调用路由探针、写账本或运行验收脚本。用户只描述正常任务，例如：

“天机，检查这个项目的登录逻辑，修复问题，补测试并运行相关测试。”

主会话必须在内部完成：

1. 晨检和宿主状态确认；
2. 选择已配置且被证明可用的模型；
3. 拆解并派发角色；
4. 执行修改和机械验收；
5. 失败返工或补偿；
6. 写入账本并向用户汇报证据。

只有在需要用户选择模型、授权修改、补充目标或处理不可恢复故障时才打断用户。不要把内部 Python 命令、探针参数或账本格式转嫁给用户。
